# Ревью перед выпуском

Дата: 2026-09-26. Код на момент ревью — коммит `1bb2d9c`, исправления — `ab8d5a2`.

Три независимых ревью (только чтение):

- **Rust:** корректность, конкуренция, обработка ошибок, идиоматичность.
- **Безопасность:** секреты, авторизация, SQL, HTML, развёртывание, история git.
- **Паритет с Python:** все хендлеры, тексты, кнопки, `callback_data`, отчёты рассылок, листы Sheets.

Плюс `cargo audit`. Каждую находку я перепроверял по коду: сначала падающий тест, потом исправление. Если серьёзность оказалась другой, это отмечено.

## Принято без изменений

| Находка | Решение |
|---|---|
| id получателя (иногда канала или админа) пишется в лог при неудачной доставке (security, MEDIUM) | LOW: Python логировал те же id; лог доступен только оператору; запрет касался стартовой строки Python со списком `ADMIN_IDS` |
| Тост «Синхронизация начата...» показывается и на повторное нажатие, пока синхронизация идёт | Итог придёт от уже идущей синхронизации (SPEC §7, Δ16) |
| `t()` паникует на неизвестный ключ | Все ключи — литералы; тест `every_key_used_by_the_bot_exists` проверяет каждый |
| При сбое SQLite в анонсе, публикации или рассылке сообщение админа остаётся «📤 …» без текста ошибки | Сбой БД логируется; Python-тексты ошибок срабатывают при сбое постановки в очередь. Редкий случай |
| Число победителей: Python принимал `1_000` и полноширинные цифры | Такой ввод не встречается; отказ с `invalid_winner_count` безопасен |
| Команда в подписи к медиа (`/start` как caption) в Python срабатывала | Не встречается в сценариях бота |
| `proc-macro-error2` не поддерживается (RUSTSEC-2026-0173, unmaintained, не CVE) | Транзитивно через макросы teloxide; исправления у апстрима пока нет; следить при обновлении teloxide |
| teloxide не разбирает видео без `mime_type` (в Bot API поле необязательно) | Telegram присылает поле; проверить на живом тесте |

Остальные расхождения с Python оформлены как осознанные отличия Δ1–Δ16 (SPEC §10, PARITY).

## Что проверено и признано корректным

- SQL везде параметризован. `format!` в SQL подставляет только константы кода.
- Токен бота не попадает в логи:
  - `redact` стоит на всех путях ошибок reqwest и teloxide;
  - ошибки polling пишутся без текста;
  - `Config` и `ServiceAccount` без `Debug`;
  - ключ Google, JWT и access_token не выводятся.
- Права админа проверяются в одной точке для callback и для сообщений. Обхода нет через `callback_data`, состояние диалога, группу или устаревшую кнопку.
- HTML: вставляются как есть только тексты админа (паритет). Username пользователей — ASCII `[A-Za-z0-9_]`, без разметки.
- Победители:
  - генератор — CSPRNG;
  - подозрительные исключаются до выбора;
  - повторный выбор возвращает уже выбранных, всё в одной транзакции.
- Импорт: одна транзакция, отказ при непустой базе, данные строк не попадают в ошибки.
- Рассылки:
  - курсор пишется до отправки;
  - сообщение, которое было «в полёте» во время падения, считается недоставленным и не повторяется;
  - 429 повторяется до `MAX_RETRIES`, 403 не повторяется.
- Пул SQLite — одно соединение, вложенных захватов пула внутри транзакции нет.
- Развёртывание:
  - unit с hardening;
  - `/etc/<name>` — `0750 root:<name>`, `bot.env` — `0600`;
  - Docker-образ distroless, non-root;
  - `.dockerignore` — список разрешённого.
- История git:
  - токенов нет (только заглушка `123456789:AAAA…` в тестах);
  - приватный ключ — только тестовый в `tests/fixtures`;
  - внутреннего имени хоста и IP нет;
  - внутренние заметки не отслеживаются.
