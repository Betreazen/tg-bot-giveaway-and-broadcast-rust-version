# Спецификация: Rust-версия бота розыгрышей и рассылок

Статус: черновик на одобрение (2026-09-25). Поведение для пользователей и админов — по
[PARITY.md](PARITY.md); здесь — как это устроено и чем отличается.

## 1. Цель и границы

Заменить Python-стек (aiogram + Postgres + Redis, три контейнера, ~86 MiB RAM, ~1.3 %
ядра) одним Rust-процессом под systemd с SQLite. Тексты, кнопки, `callback_data`,
права и сценарии — как в Python `9a4c9c6`. Все данные Postgres переносятся без потерь.

Вне задачи: новые функции, смена текстов, веб-интерфейс, несколько экземпляров бота.

## 2. Стек

| Что | Выбор | Почему |
|---|---|---|
| Telegram | `teloxide 0.17` (rustls, без default features) | эталон |
| БД | `sqlx 0.8` SQLite, 1 соединение, WAL, `synchronous=FULL`, `busy_timeout` | эталон; один процесс |
| Runtime | `tokio` current_thread | эталон |
| Логи | `tracing` → stdout → journald, `NO_COLOR=1` | эталон |
| Время | `chrono` без default features | МСК-расчёты и форматирование |
| Случайность | `rand` (`ThreadRng` — CSPRNG с сидом из ОС) | честный выбор победителей |
| Google | прямые REST-вызовы OAuth2 + Sheets v4 через `reqwest` (уже есть в дереве у teloxide); подпись JWT RS256 — крейтом, который уже тянет rustls (`ring`), либо `jsonwebtoken` | без gspread-аналогов |
| Прочее | `serde`, `serde_json`, `anyhow` | эталон |
| Тесты | `wiremock` (Telegram и Google), `tempfile` | реальный токен не нужен |

Минимум зависимостей: каждая новая сверх эталона — только с обоснованием.

## 3. Данные

Файл `DATA_DIR/bot.db`. Схема задаётся SQL-миграциями, версия — `PRAGMA user_version`.
Время хранится как TEXT RFC 3339 в UTC с микросекундами (`2026-07-27T13:01:02.123456Z`) —
без потери точности из `timestamptz`, строки сортируются лексикографически.

Таблицы (перенос 1:1 из Postgres, id сохраняются):

- `users(user_id PK, username, joined_at, is_suspicious)`
- `giveaways(id PK AUTOINCREMENT, start_at, end_at, description, num_winners CHECK>0,
  is_active, announce_text, announce_media_file_id, announce_media_type,
  created_by_admin_id, created_at, ended_at, CHECK end_at>start_at)` +
  частичный уникальный индекс «не больше одного активного» (в Python это держалось только кодом).
- `participants(id PK AUTOINCREMENT, giveaway_id, user_id, joined_at, username_snapshot,
  giveaway_end_snapshot, UNIQUE(giveaway_id,user_id))`
- `winners(id PK AUTOINCREMENT, giveaway_id, user_id, username_snapshot,
  giveaway_end_snapshot, created_at, UNIQUE(giveaway_id,user_id))`

Новые (заменяют Redis и память процесса):

- `dialogues(user_id PK, state JSON, updated_at)` — состояния мастеров и верификации.
  Переживают рестарт (в Python — Redis).
- `verification_attempts(giveaway_id, user_id, attempts, PK(...))` — счётчик ошибок;
  блок = `attempts ≥ 3`. Ключ содержит розыгрыш, поэтому 30-дневный TTL Redis не нужен:
  новый розыгрыш — новые попытки, как в Python.
- `mailings(...)` — очередь и прогресс рассылок (раздел 5).

Не переносится: `admin_drafts` (0 строк, код не используется), `alembic_version`.

### Перенос из Postgres

Подкоманда `bot import <dir>` читает `users.jsonl`, `giveaways.jsonl`,
`participants.jsonl`, `winners.jsonl` — их выгружает скрипт переключения через
`docker exec … psql -At` с `SET TIME ZONE 'UTC'` и `SELECT row_to_json(t) FROM <table> t`.

- Отказ, если в целевой БД уже есть данные (никакого слияния поверх).
- Всё в одной транзакции: либо перенесено всё, либо ничего.
- Сверка после вставки: число строк каждой таблицы = числу строк файла, число
  подозрительных, `max(id)`, число участников по каждому розыгрышу. Итог печатается;
  скрипт сравнивает его с `count(*)` из Postgres и при расхождении откатывает переключение.
- Redis не переносится: FSM-сессии (сейчас 17, все устаревшие) теряются. Скрипт
  останавливается, если найдёт ключи `verify_*` (сейчас их нет — активного розыгрыша нет).

## 4. Обработка апдейтов

- Long polling (10 с при HTTP-таймауте 17 с — урок эталона), только `Message` и `CallbackQuery`.
- Апдейты одного пользователя обрабатываются по очереди (per-user lock) — двойное
  нажатие не создаёт двойных записей.
- Состояние диалога берётся из `dialogues` и меняется в той же транзакции, что и данные.
- Проверка админа — в одной точке перед всеми админскими ветками (как middleware в Python).
- Отправка — `parse_mode=HTML`, как в Python; текст админа вставляется как есть.
- Ошибки логируются через redact (токен → `[REDACTED]`); `ADMIN_IDS` и `CHANNEL_ID`
  в лог не пишутся (Python их логировал).

## 5. Рассылки (анонсы, результаты, рассылки)

Рассылка — строка в `mailings`: тип и содержимое, цель (канал / пользователи / админы),
RPS, курсор, счётчики, чат и id сообщения админа для отчёта, статус `queued/running/done`.

- Выполняет один фоновый worker, по очереди (FIFO). Хендлер только ставит задачу и
  показывает «📤 …», как в Python.
- Скорость как в Python: отправки последовательно, после каждой пауза `1/RPS`
  (`BROADCAST_RPS`/`ANNOUNCE_RPS`; анонсы — `ANNOUNCE_RPS`, результаты пользователям —
  `BROADCAST_RPS`, результаты админам — `ANNOUNCE_RPS`).
- Получатели — снимок: пользователи с `joined_at ≤ создания рассылки`, по возрастанию
  `user_id`, пачками по 500.
- **Без дублей после рестарта**: курсор (последний `user_id`) фиксируется в БД до
  отправки. После падения worker продолжает со следующего; сообщение, которое было
  в полёте, считается «не доставлено» (не больше одного на падение), повторно не шлётся.
- 429 → ждать `retry_after` и повторить, до `MAX_RETRIES` раз (в Python — один повтор,
  `MAX_RETRIES` не использовался). 403 и прочие ошибки → «не доставлено», без повтора
  (повтор после сетевой ошибки мог бы дать дубль).
- Пост в канал делается первым, отметка о нём хранится — после рестарта не повторяется.
- В конце сообщение админа редактируется итоговым текстом Python-версии; после
  рестарта — тоже. Прогресс пишется в лог каждые 100 адресатов.

## 6. Победители

Одна транзакция: если у розыгрыша уже есть победители — вернуть их (повторный выбор
невозможен); иначе взять участников, исключить подозрительных, выбрать
`min(N, легитимных)` через CSPRNG и записать. Снимки — как в Python
(`giveaway_end_snapshot = ended_at или end_at`).

## 7. Google Sheets

По кнопке «📊 Синхронизация Google Sheets», как в Python: 5 листов (Overview, Users,
Participants, Winners, Giveaways Summary) с теми же заголовками и форматом дат (МСК),
лист создаётся при отсутствии, расширяется под объём, очищается и пишется одним `update`
(`RAW`). Access-token — JWT сервисного аккаунта (scope spreadsheets + drive).
Выполняется в фоне, одна синхронизация за раз; итог — те же три сообщения
(«✅ …успешно завершена!», «⚠️ Синхронизация не выполнена…», «❌ Ошибка…»).
`SHEETS_SYNC_ENABLED=false` или нет ключа → «⚠️ …не выполнена…», как в Python.

## 8. Конфигурация

Переменные: `BOT_TOKEN`, `ADMIN_IDS`, `CHANNEL_ID`, `JOIN_URL`, `BROADCAST_RPS`(20),
`ANNOUNCE_RPS`(20), `MAX_RETRIES`(5), `SHEETS_SYNC_ENABLED`(false),
`GOOGLE_CREDENTIALS_PATH`, `SPREADSHEET_ID`, `LOG_LEVEL`(INFO), `DATA_DIR`.
Все значения trim (CRLF, пробелы). Postgres/Redis-переменные игнорируются.

Режимы запуска: без аргументов — бот; `--check` (конфиг, миграции, `quick_check`,
без Telegram); `--healthcheck` (SQLite + свежесть heartbeat, как в эталоне);
`--version`; `import <dir>`.

## 9. Развёртывание

Как у бота опросов: бинарник собирается локально в Docker (`rust:1.98.1-bookworm`),
на сервере — `/opt/tg-bot-giveaway-and-broadcast/bot`,
`/var/lib/tg-bot-giveaway-and-broadcast` (0700), `/etc/tg-bot-giveaway-and-broadcast/bot.env`
(0600) и `service_account.json` (0640 root:сервис), unit с `Restart=always`,
`MemoryMax`, `CPUQuota`, hardening. Переключение — скриптом с автооткатом: бэкап →
остановка Python → выгрузка → `import` + сверка → `--check` → `enable --now` → проверки.

## 10. Осознанные отличия от Python (Δ)

| # | Отличие | Причина |
|---|---|---|
| Δ1 | Состояния мастеров и верификации переживают рестарт; при переключении текущие Redis-сессии теряются | SQLite вместо Redis; админов предупредить |
| Δ2 | Рассылки — фоновая очередь с прогрессом в БД, продолжаются после рестарта без дублей; 429 повторяется до `MAX_RETRIES` | требование надёжности |
| Δ3 | Победители — CSPRNG; повторный выбор для того же розыгрыша возвращает уже выбранных | честность, идемпотентность |
| Δ4 | В БД запрещено два активных розыгрыша одновременно | было только в коде |
| Δ5 | `/start` и мастера работают только в личных чатах; `/admin` в группе отвечает, как в Python | состояние ключуется по пользователю; бот по `JOIN_URL` открывается в личке |
| Δ6 | Callback без обработчика (старые кнопки, «Назад» у выбора победителей) гасится без текста, а не висит «часиками» | UX, поведение не меняется |
| Δ7 | «Назад» в мастере рассылки возвращает к выбору типа (в Python кнопка мёртвая) | очевидная ошибка Python |
| Δ8 | Лог — journald, без `logs/bot.log`; `ADMIN_IDS`/`CHANNEL_ID` не логируются | эксплуатация, приватность |
| Δ9 | Пауза `1/RPS` и после неудачных отправок (Python — только после успешных) | мягче к лимитам; ~1.4 % адресатов |
